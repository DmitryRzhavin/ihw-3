# ИДЗ №3 АКОС — вариант 32 «Кухня ресторана»

Консольная имитационная программа на C11 для Linux с взаимодействующими
процессами. Посетители, официанты, повара и координатор кухни работают
как самостоятельные участники модели.

В ИДЗ №1 использовалась последовательная дискретно-событийная модель,
в ИДЗ №2 — потоки `pthread`. В этой реализации участники имеют отдельные PID,
а обмен данными организован средствами POSIX IPC. Формат описания меню
сохранён относительно предыдущих работ.

## Реализации

| Программа | Запуск участников | Взаимодействие |
|---|---|---|
| `restaurant_unnamed` | дочерние процессы общего родителя | POSIX shared memory, безымянный межпроцессный семафор |
| `restaurant_named` | дочерние процессы общего родителя | POSIX shared memory, именованный семафор |
| `restaurant_shm` | независимо запускаемые процессы | POSIX shared memory, именованный семафор |
| `restaurant_mq` | независимо запускаемые процессы | POSIX-очереди сообщений, именованный семафор |

Все четыре цели сборки используют общее ядро предметной модели.
В варианте с очередями сообщений состояние находится только у координатора;
разделяемая память для передачи данных не используется.

## Возможности

- отдельный процесс каждого посетителя, официанта и повара;
- координатор кухни в процессе-владельце сеанса;
- последовательности зависимых операций;
- четыре вида оборудования с учётом конкретной свободной единицы;
- ограниченные кухонная очередь и зона передачи готовых блюд;
- приоритеты заказов FIFO/LIFO;
- явные заказы либо генерация состава по `seed`;
- постоянные либо индивидуальные интервалы прихода;
- явная отмена заказов при отсутствии нужного оборудования;
- сборка заказа только после получения всех его блюд;
- обработка SIGINT/SIGTERM, итоговая статистика и очистка IPC;
- событийный журнал через файловые дескрипторы.

## Основные модули

`config.c` отвечает за параметры, меню и заказы. `model.c` реализует состояния,
действия участников, работу координатора, инварианты и журнал. `main.c`
содержит CLI, создание процессов, IPC-транспорт, сигналы и освобождение
ресурсов. Общие структуры и интерфейсы находятся в `model.h`.

`build.sh` — обёртка сборки. `run_independent.sh` — обёртка независимого
запуска координатора и участников для shared-memory и MQ-вариантов.
Эти два скрипта не являются тестами.

## Параметры модели

Число посетителей задаётся ключом `visitors` в выбранной конфигурации.
Обработка ключа отмечена комментарием в `src/config.c`. Режим конечный.
При явных `order=` количество заказов должно совпадать с числом посетителей;
при автоматической генерации достаточно изменить `visitors`.

Формат блюда: `dish=Soup|stove:3,table:1` — сначала плита, затем стол.
Меню задаётся до строк заказов. Повторяющиеся блюда в заказе считаются
разными экземплярами. Значение вместимости `0` снимает дополнительное
ограничение очереди в пределах размера модели.

Оборудование: `stove`, `oven`, `grill`, `table`. Интервалы задаются
`arrival_interval` либо списком `arrival_intervals`; в списке первый элемент
задаёт задержку первого посетителя. `unit_ms` определяет реальную длительность
одной единицы времени. `priority` принимает `fifo` либо `lifo`.

Пределы: 1–64 посетителя, 1–16 официантов, 1–16 поваров, 1–16 типов блюд,
1–8 блюд в заказе, 1–8 шагов в блюде, 0–16 единиц каждого вида оборудования.
Положительная вместимость очереди — до 512, длительность операции — до
100000, `unit_ms` — 1–10000. Прочие числовые параметры ограничены 1000000.

## Проверки

Тесты вынесены в Bash-скрипты и выполняются только при их отдельном запуске.
Программа ресторана и обычная сборка не запускают функциональные тесты.
Python, дополнительные тестовые библиотеки и сетевой доступ не нужны.
Для анализа вывода используются `awk` и стандартные утилиты Linux.

- `run_tests.sh` запускает 44 функциональные проверки четырёх реализаций,
  C-тест ядра и, при наличии CMake-сборки, зарегистрированные CTest-тесты.
- `check_log.sh` проверяет зависимости операций, исключительность оборудования,
  сборку, правильность выдачи и согласованность итогового журнала.
- `run_sanitizers.sh` собирает версии с UBSan и повторяет тот же набор.
- `model_test.c` проверяет FIFO/LIFO, занятость повара, оборудование,
  запрет завершения чужой операции и обнаружение нарушенного счётчика.

Набор включает обычное обслуживание, обе ограниченные очереди, LIFO,
генерацию заказов, отмену невыполнимых заказов, SIGINT/SIGTERM, повторный
запуск, нагрузку и защиту от второго владельца сеанса. После запусков
сравниваются списки IPC-объектов до и после завершения.
Это функциональные проверки, а не измерение процента покрытия исходного кода.

Обновлённые Bash-проверки выполнены обычной и UBSan-сборкой: 44 из 44
проверок прошли в обоих случаях, C-тест ядра также прошёл.
Среда проверки — Linux x86_64, GCC 15.2. CMake/CTest и ASan в этой среде
не проверялись; пользовательская среда GCC 13.3 требует повторного запуска.

## Ограничения

Короткий опрос состояния с паузой 2 мс упрощает протокол, но увеличивает
число обращений к IPC. Приготовление происходит вне критической секции.
MQ-транзакции сериализованы именованным семафором, чтобы участник не
получил чужой ответ из общей очереди.

Зона готовых блюд является передаточным буфером: координатор забирает блюда
по одному и собирает заказ отдельно. Поэтому заказ может содержать больше
блюд, чем вместимость этой зоны.

По умолчанию сеанс ограничен 60 секундами; CLI допускает до 3600.
Одинаковый `seed` воспроизводит состав заказов, но не порядок конкурентных
событий. SIGKILL и аварийная смерть участника не восстанавливаются;
после них автоматическая очистка IPC не гарантируется.

Каталоги сборки и журналы создаются во время работы и исключены из Git.
Подробное описание архитектуры, инвариантов и результатов приведено в отчёте.
